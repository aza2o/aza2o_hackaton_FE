## 0. 문서의 범위

이 문서는 **화면을 어떻게 구현하는가**를 다룬다. 기능 근거·리스크·아키텍처 결정은 메인 기획서에 있으며, 여기서는 그것을 전제로 **화면 인벤토리 · 네비게이션 · 디자인 토큰 매핑 · 화면별 API 연동 · 데이터 계층**을 확정한다.

이 문서를 쓰는 시점 기준, 화면은 **두 개의 Figma 파일**에 나뉘어 있다.

| 파일 | 내용 |
|---|---|
| 기존 디자인 파일 (`7zokAwX2p7oJe8lQETNRvq`) | 설정, 홈(낮/오프·나이트/이브닝 2 variant), Style Guide 원본 |
| 신규 제작 파일 (`sSdQWzM275fF05l9oqPyoe`) | Style Guide 복제본, 로스터 입력·확인, AI 리포트, 피부·손 루틴 |

**신규 파일의 텍스트는 Pretendard가 아니라 Noto Sans KR로 렌더링돼 있다** — 제작에 쓰인 원격 Figma 실행 환경이 커스텀 업로드 폰트(Pretendard)에 접근할 수 없었기 때문이다. 텍스트 스타일 이름(`Heading/01` 등)은 기존과 동일하게 맞춰뒀으므로, **Flutter 구현에서는 이 이름 그대로 Pretendard로 매핑**하면 된다. 크기·굵기·줄간격 수치는 전부 원본과 동일하다.

> **2026-08-18 아키텍처 확정**: 계산 로직(4모델 DLMO 추정, 넛지 시뮬레이션)은 전부 **클라이언트(Dart, `flutter_engine/`)** 에서 돈다 — 백엔드 팀과 합의 완료. 서버(`logic/`)는 계산 엔진이 아니라 **엑셀 로스터 파싱 전용 엔드포인트 하나**만 남는다(§4-2 참고). 이 문서의 "서버 `/plan`" 관련 서술은 전부 이 결정 기준으로 갱신했다. 실측 헬스 데이터를 lux(t)·Process S에 반영하는 설계(`SHIFT_실측데이터_통합_기획서.md`)는 컨셉은 유효하나, Python `observations.py`가 아니라 **Dart 쪽 lux(t) 포팅 시 그 원칙(3계층 fallback, 무데이터 회귀 테스트)을 그대로 적용**해야 한다 — 아직 미착수.

## 2. 정보구조(IA) / 네비게이션

```
하단 탭(2개) ── 홈 ─┬─ (헤더 아이콘) 캘린더 → ??? (§7-1 확인 필요)
                    └─ (헤더 아이콘) 게이지(skin) → 피부·손 루틴 (추정)
              └─ 설정

푸시 플로우 (탭 아님)
  로스터 입력 → 로스터 확인 → (완료 시 홈으로 복귀)
  AI 리포트 (진입 경로 미확정)
  피부·손 루틴 (진입 경로 홈 헤더 아이콘으로 추정)

최초 실행
  온보딩 → 권한 온보딩 → 로스터 입력 → 홈
```

### 2-1. 확인이 필요한 네비게이션 갭

- 홈 화면 헤더의 캘린더 아이콘과 게이지("skin") 아이콘이 각각 어디로 연결되는지 **prototype 링크가 아직 없어 추정치**다. 캘린더 → 로스터 확인 또는 AI 리포트, 게이지 → 피부·손 루틴일 가능성이 높지만 확정은 아니다.
- 탭바는 홈/설정 2개뿐이라, 로스터·AI 리포트·피부 트랙은 전부 **홈에서 파생되는 2차 화면**이다. 프론트 라우팅 설계 시 이 화면들을 별도 탭이 아니라 홈의 하위 스택으로 구성해야 한다.

## 3. 디자인 토큰 → Flutter 매핑

### 3-1. 컬러

Figma 변수 컬렉션 3개를 그대로 Dart 상수/`ThemeExtension`으로 옮긴다.

| Figma 컬렉션 | 변수 수 | Flutter 대응 |
|---|---|---|
| `Design Colors` (Primary 50~900, Light/Dark/IC-Light/IC-Dark 4모드) | 10 | `AppColors.primary50`~`primary900` — 4모드는 전부 같은 값이므로 라이트/다크 분기 불필요 |
| `System Colors` (Gray/Error/Warning/Success/Information + 시맨틱 Text·Border) | 34 | `ColorScheme` 커스텀 확장 또는 `AppColors` 상수 클래스 |
| `Numbers` (4/8/12/16/20/24/28) | 7 | `AppSpacing` 상수 (`xs`~`xl` 네이밍 권장) |

시맨틱 컬러는 원본에서도 로컬 별칭이다 (`Text/Primary` → `Gray/900` 등). Flutter에서도 원시값을 직접 쓰지 말고 시맨틱 이름으로 접근하게 해서, 나중에 다크모드 도입 시 별칭 값만 바꾸면 되게 한다.

### 3-2. 타이포그래피

19개 텍스트 스타일(`Heading/01~04`, `Subtitle/01~04`, `Body/01~02`, `Caption/01~03`, `Button/01~06`)을 `TextTheme` 확장 또는 커스텀 `AppTypography` 클래스로 그대로 옮긴다. 폰트는 **Pretendard**를 Flutter 에셋으로 번들(`Bold`/`SemiBold`/`Regular` 최소 3 굵기 — Noto Sans KR 대체본과 달리 실제 앱은 SemiBold를 그대로 쓸 수 있다).

### 3-3. 글래스 카드 이펙트

기존 디자인의 카드(`glass` 프레임)는 Figma 네이티브 `GLASS` 이펙트(refraction 1, depth 16, lightAngle 315, lightIntensity 0.6)를 쓴다. **Flutter에 이 이펙트의 직접 대응 API가 없다** — `BackdropFilter` + `ImageFilter.blur` + 반투명 흰색 오버레이 + 옅은 `BoxShadow`(radius 20, offset (0,8), opacity 0.04)로 근사해야 한다. 픽셀 단위로 동일하게는 안 나올 수 있다는 걸 미리 인지하고, 실기기에서 톤을 눈으로 맞추는 튜닝 단계를 마일스톤에 넣는 걸 권한다.

## 4. 화면별 기능 명세

### 4-1. 홈 (낮/오프 · 나이트/이브닝)

| 항목 | 내용 |
|---|---|
| 데이터 소스 | 로컬 Dart 엔진(`shift_circadian_engine`) 계산 결과(다음 근무·권장 취침·오늘의 행동 2건) **+ 클라이언트 `HealthSignalSource`**(회복 상태 3종) — **두 소스를 합쳐야 한다**(둘 다 클라이언트 내부이므로 네트워크 왕복 없이 합성 가능) |
| 엔진 출력 | `dlmoClock`(권장 취침 앵커), `nudges[].message`/`nudges[].at`(오늘의 행동 카드) — 필드명은 Python `Plan.to_dict()`와 동일하게 맞춰서 참고 코드 재사용 |
| 클라이언트 전용 | "최근 회복 상태"의 수면시간·HRV·안정심박은 엔진 출력에 없다. §6-4 `HealthSignalSource` 어댑터에서 직접 조회해서 UI에 병합 |
| 변형 조건 | 오늘 근무 타입이 D/O면 낮/오프 배경(웜톤), E/N이면 나이트/이브닝 배경(쿨톤) — 근무 타입은 로스터에서 계산 |
| 액션 | "완료" 버튼 → 행동 로그 기록(로컬 우선, 서버 동기화는 후순위 가능) |

**넛지 문구 원칙**: 기존 "오늘의 행동" 카드는 예상 효과·근거 문구를 노출하지 않는다. AI 리포트 화면에만 아주 작은 캡션으로 넣기로 확정했으니, 홈 화면 구현 시 이 원칙을 유지한다(§4-3 참조).

#### 4-2-1. `POST /roster/parse` API 계약

| | |
|---|---|
| 요청 | `multipart/form-data`: `file`(바이너리, .xlsx/.xls), `user_name`(string, 본인 행 매칭용), `year_hint`/`month_hint`(int, optional — 클라이언트가 현재 보고 있는 월을 보내면 §5-2-3 "연도 누락" 케이스를 대부분 회피 가능), `known_code_mappings`(optional, `{"연차":"O"}` 형태 — 이 사용자가 이전에 학습시킨 매핑을 클라이언트가 들고 있다가 매번 같이 보낸다) |
| 성공 응답 | `{"status":"ok", "year":2026, "month":8, "shifts":{"1":"D","2":"D",...}, "unmapped_codes":[]}` |
| 본인 행 모호 | `{"status":"needs_row_selection", "candidates":[{"row":3,"name":"이수정"},{"row":7,"name":"이수정"}]}` — 클라이언트가 사용자에게 재확인 후 `row` 인덱스와 함께 재요청 |
| 미등록 코드 존재 | `{"status":"ok", "shifts":{...}, "unmapped_codes":["연차","교육"]}` — 클라이언트는 이 배열이 비어있지 않으면 매핑 질문 UI를 띄운다 |
| 실패 | `{"status":"error", "message":"..."}`, HTTP 4xx |
| **개인정보 처리(협상 불가, 개발기획서 §5-2-4)** | 서버는 본인 행만 추출한 뒤 **원본 파일을 응답 직후 즉시 폐기**한다. 타인 행은 어떤 형태로도 저장·로그 금지. `year_hint`/`month_hint`를 안 보내서 서버가 연도를 못 정하는 경우에만 `needs_year` 상태를 추가로 정의해도 되지만, 클라이언트가 항상 현재 보는 월을 같이 보내면 이 분기 자체가 거의 발생하지 않는다 |
| 구현 위치 | `logic/main.py`에 엔드포인트 추가. 파싱 규칙(피벗 헤더 탐지, 병합 셀, 날짜 행 앵커링)은 개발기획서 §5-2-3 표 그대로 |

### 4-4. 피부·손 루틴

| 항목 | 내용 |
|---|---|
| F1 (AM/PM 루틴) | Dart 엔진 출력 `sleep[]`에서 `kind: "main"`인 가장 가까운 창의 `start`(취침)/`end`(기상)를 앵커로 사용. **신규 로직 불필요** — 엔진 값 재사용 |

| 금지 표현 | 진단·효능 표현, 피부 점수/게이지, 시간축 그래프로 표시되는 "수분 지수" — 절대 넣지 않는다 (피부 트랙 기획서 §2, §5) |

- 배터리 최적화 예외 재요청
- 웨어러블 연동 라벨은 플랫폼 변수로 처리(`Apple Health`/`Health Connect` 하드코딩 금지, §6-4/§6-5)

## 5. 데이터 계층 / 상태관리

```
UserProfile (로컬 캐시 + 서버 profile 필드와 동기화)
  ├─ shift_timings, workplace_lighting, bedroom_lighting
  ├─ commute_minutes, latitude, longitude
  └─ (신규) uv_grid_xy — F2용 기상청 격자 좌표, 최초 계산 후 캐시

Roster (로컬 저장, 월 단위)
  └─ 코드 매핑 테이블 (사용자별 재사용, §5-2-3)

Plan (로컬 Dart 엔진 계산 결과 캐시)
  ├─ 하루 1회 재계산 (온보딩, 로스터 변경, 헬스 동기화 시) — 전부 로컬, 네트워크 불필요
  ├─ nudges → 로컬 알림 예약 큐로 변환
  └─ 오프라인에서도 항상 최신 계산 가능 (서버 의존 없음 — 개발기획서 §4 "오프라인에서도 넛지가 정상 발화" 원칙이 서버 캐시가 아니라 로컬 계산으로 달성됨)

HealthSignalSource (§6-4 어댑터, 플랫폼 분기)
  ├─ sleepSessions, daylight, hrvNormalized, restingHeartRate
  └─ 홈 화면 "최근 회복 상태" + F1 앵커 보정에 사용

로컬 전용 상태 (서버 미연동)
  ├─ 손 보습 카운터 (F3)
  └─ 넛지 "완료" 체크 로그 (동기화 여부 미정)
```

## 6. 플랫폼 분기 요약

세부는 개발기획서 §6을 그대로 따르되, 계산 로직 위치만 서버→클라이언트로 갱신해서 읽는다. 프론트 작업 순서 관점에서만 요약:

- UI·로스터·액토그램·넛지·**계산 엔진(`shift_circadian_engine`)**은 100% 공유 (Dart이므로 iOS/Android 동일 코드)
- `HealthSignalSource` 구현체만 iOS/Android 분기 (`IosHealthSource`/`AndroidHealthSource`)
- iOS는 세션 스티칭 로직 필요, Android는 dedup + 출처 필터 필요 — 둘 다 홈 화면의 "회복 상태" 정확도에 직결되므로 해당 화면 QA 시 반드시 실기기 두 플랫폼에서 확인
