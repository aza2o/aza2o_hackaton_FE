# SHIFT 데이터 소스 점검 — 뭐가 진짜고 뭐가 가짜인가

> 코드 실사 기반. `shift_app`의 모든 화면 + `logic/main.py`(서버) 확인.
> v1 · 2026-08-18

## 0. 결론 먼저

- **네트워크 호출이 앱 어디에도 없다.** `pubspec.yaml`에 `http`/`dio` 계열 패키지 자체가 없고, 코드에서 `http.` 호출 0건. `POST /roster/parse`(§4-2-1에 계약까지 확정된 유일한 서버 API)를 부르는 코드가 없다 — 로스터 입력 화면은 그냥 다음 화면으로 넘어갈 뿐이다.
- **서버(`logic/main.py`)는 구 아키텍처 그대로 남아있다.** `/plan`, `/render/{kind}` 두 엔드포인트가 있는데, 이건 "계산을 서버에서 한다"던 옛날 설계다. 2026-08-18 아키텍처 확정(`SHIFT_프론트엔드_기획서.md` 상단)으로 계산은 전부 `flutter_engine`으로 이관됐으니 이 두 엔드포인트는 폐기 대상이고, 대신 있어야 할 `POST /roster/parse`는 **서버 코드에 아예 없다.**
- 지금 화면에 뜨는 값은 세 종류로 나뉜다: **① 실제 계산됨**(엔진이 진짜 계산), **② 데모/목업**(가짜지만 구조는 진짜처럼 동작), **③ 완전 하드코딩**(그냥 고정 텍스트, 로직 자체가 없음). 아래 표에서 구분했다.

## 2. 서버(`logic/main.py`) 실사 — 코드 vs 최신 아키텍처 문서 불일치

| 엔드포인트 | 코드에 있음? | 최신 문서(§4-2-1) 기준 |
|---|---|---|
| `POST /plan` | ✅ 있음 (구현됨) | ❌ **폐기 대상.** DLMO·넛지 계산은 `flutter_engine`으로 이관 확정. 이 엔드포인트를 계속 쓰면 계산이 서버/클라이언트 두 군데서 따로 돌아 서로 다른 답이 나올 위험 |
| `POST /render/{kind}` | ✅ 있음 (구현됨) | ❌ **폐기 대상.** 액토그램은 `CustomPainter`로 확정, PNG 렌더링 서버 경로 안 씀 |
| `GET /health` | ✅ 있음 | 유지해도 무방(헬스체크용, 무해) |
| `POST /roster/parse` | ❌ **코드에 없음** | ✅ **이게 유일하게 진짜 필요한 엔드포인트.** 계약은 이미 확정돼 있음(§4-2-1) — 구현만 안 됨 |

즉 서버는 "필요 없어진 것 2개는 아직 살아있고, 필요한 것 1개는 없는" 상태다.

## 3. 그래서 API로 뭘 주고받아야 하는가

### 3-1. 진짜 서버 API — `POST /roster/parse` 하나뿐

`SHIFT_프론트엔드_기획서.md` §4-2-1에 이미 계약이 있다. 다시 정리하면:

**보내는 것 (클라이언트 → 서버)**
```
multipart/form-data
  file                    바이너리 (.xlsx/.xls)
  user_name               string — 본인 행 매칭용
  year_hint, month_hint   int, optional — "연도 누락" 케이스 회피용
  known_code_mappings     optional, {"연차":"O"} 형태 — 이 사용자가 이전에 학습시킨 매핑
```

**받는 것 (서버 → 클라이언트)**
```
성공          {"status":"ok","year":2026,"month":8,"shifts":{"1":"D",...},"unmapped_codes":[]}
본인 행 모호   {"status":"needs_row_selection","candidates":[{"row":3,"name":"이수정"},...]}
미등록 코드    {"status":"ok","shifts":{...},"unmapped_codes":["연차","교육"]}
실패          {"status":"error","message":"..."}  (HTTP 4xx)
```

**개인정보 제약(협상 불가)**: 서버는 본인 행만 추출한 뒤 원본 파일 즉시 폐기, 타인 행은 어떤 형태로도 저장·로그 금지.

이거 하나만 구현하면, 클라이언트는 응답의 `shifts`를 `List<ShiftType>`로 변환해서 `AppState.saveRoster()`에 넣으면 된다 — 지금 `RosterConfirmScreen`이 가짜로 채우고 있는 그 자리에 그대로 꽂힌다.

### 3-2. 서버 API가 아닌 것 — 헷갈리면 안 되는 지점

"서버와 데이터를 주고받는다"는 개념 자체가 없는 데이터가 있다. 사용자가 서버 API 설계를 요청하면서 이 둘을 섞으면 안 되므로 명확히 구분:

| 데이터 | 어디서 오나 | 서버 관여? |
|---|---|---|
| 수면 세션, 심박, HRV, 일광 노출 | **기기 자체**(iOS HealthKit / Android Health Connect) — `HealthSignalSource` 인터페이스(§6-4 개발기획서, 이미 코드에 있음) | ❌ 전혀 없음. 네이티브 플랫폼 API 직접 호출 |
| DLMO 위상, 오늘의 넛지, 목표 취침/기상 | `flutter_engine`(`buildNudgePlan` 등) — 로컬 계산 | ❌ 전혀 없음. 로스터+프로필+수면이력만 있으면 오프라인에서도 계산됨 |
| 액토그램(수면/근무/DLMO 그래프) | 동일 — `flutter_engine`을 CustomPainter에 연결하면 됨 | ❌ |
| 로스터 원본 파싱 | 엑셀 파일 | ✅ 서버(§3-1의 그 엔드포인트) |

### 3-3. 애매하게 남은 것 — 결정 필요

- **AI 리포트의 "DLMO 평균 25분 지연" 같은 효과 캡션.** 원래 설계(`logic/nudge.py`)는 4모델 ODE로 반사실 시뮬레이션을 돌려서 나온 값인데, 이건 연산량이 있어서 클라이언트에서 매번 돌리기엔 무거울 수 있다. 두 갈래: (a) 이것도 Dart로 포팅(엔진 코어는 이미 검증됐으니 불가능하진 않음), (b) 서버에 이 계산만 노출하는 엔드포인트를 하나 더 둔다(`POST /nudge-effects` 같은 걸로, 로스터+프로필만 보내고 캐시 가능). 지금은 둘 다 없어서 그 캡션들이 통째로 하드코딩돼 있다.
- **`AppState`가 메모리 전용이라 앱을 껐다 켜면 다 날아간다.** 이건 서버 API 문제가 아니라 로컬 저장(Drift) 문제 — `docs/SHIFT_프론트엔드_구현체크리스트.md` §5 참고.
