# SHIFT 엔진 — 실측 데이터 통합 기획서

> **한 줄 요약**: 지금 엔진은 "근무표대로 살았다면"을 계산한다. 실제로 어떻게 살았는지를 반영하는 경로를 만든다.
>
> **중요**: 이 작업은 ODE 모델을 건드리지 않는다. 모델 **입력을 만드는 층**과 **Process S 층**만 바꾼다.

---

## 0. 현재 상태 진단

### 0-1. 코드 실사

| 모듈 | 현재 입력 | 실측 데이터 반영 |
|---|---|---|
| `light.py` | 근무표 + 온보딩 조명 상수 + 위경도 | ❌ 없음 |
| `phase.py` | `light.py`가 만든 `(t, lux)` | ❌ (의도적 — 유지) |
| `pressure.py` | `light.py`의 **계획** `SleepWindow` | ⚠️ 시그니처만 존재 |
| `nudge.py` | 위 전부 | ❌ 상위 층 따라감 |
| `pipeline.py` | `roster`, `start_date`, `profile` | ❌ 실측 인자 자체가 없음 |

### 0-2. 죽은 코드

- `phase.scale_steps_to_activity()` — 구현돼 있으나 어디서도 호출되지 않음. 활동 기반 위상 추정 경로가 미완성.
- `pressure.se_discount(sleep_efficiency)` — `None`만 들어오므로 항상 할인 계수 1.0. 사실상 no-op.

### 0-3. 이게 왜 문제인가

Day 근무자가 새벽 1시 30분에 잤다고 하자.

```
현재 엔진 : 22:00 취침 가정 → 22시 이후 lux = BEDROOM_LUX(1~200)
실제      : 01:30까지 거실 조명 → 3.5시간 × ~200 lux 야간 노출
```

이 3.5시간은 **위상을 실제로 지연시킵니다.** 엔진은 이 사람이 정렬돼 있다고 판단하고 "개입 불필요"를 출력하지만, 실제로는 밀려 있습니다. 근무표만 쓰면 이 오차를 구조적으로 못 잡습니다.

## 1. 설계 원칙

### 원칙 1 — ODE 우변은 불변

수면·심박·활동량을 `Hannay19` 방정식에 입력으로 넣지 않는다. 넣는 순간:
- 결과를 원인 자리에 넣는 순환이 됨 (수면은 시계의 **출력**)
- Walch/Hannay 계보의 재현성 논거 소멸 — SHIFT의 유일한 근거 자산

실측 데이터는 **lux(t)를 만드는 재료**와 **Process S 입력**으로만 들어간다.

### 원칙 2 — 3계층 우선순위 (fallback)

```
1순위  실측 (수면 로그, 걸음 수 기반 추정)
2순위  온보딩 선언 (사용자가 말한 평소 취침시각)
3순위  기본 상수 (constants.py)
```

각 시간 슬롯마다 독립적으로 결정한다. "3일치 실측 + 13일치 계획"이 정상 동작해야 한다.

### 원칙 3 — 데이터 0에서도 동작

교대근무 간호사는 워치를 안 차거나, 나이트 후 낮잠은 기록이 안 되거나, 근무 중엔 벗는다.
**실측이 없어도 Day 1부터 결과가 나와야 한다.** 실측은 정확도를 올리는 것이지 동작 조건이 아니다.

### 원칙 4 — 개인 내 상대 비교만

절대 회복량·절대 lux 주장 금지. 기존 `constants.py` 방침 그대로 유지.

## 2. 아키텍처 변경

### 2-1. 신규 모듈 — `observations.py`

실측 데이터의 **단일 진입점**. 다른 모듈이 원시 헬스 데이터를 직접 만지지 않게 한다.

```
app/engine/observations.py

  ObservedSleep      실제 수면 구간 (start, end, efficiency|None, source)
  ObservedSteps      시간별 걸음 수
  Observations       위 둘의 컨테이너 + 유효성 검사

  ingest_health(raw)         → Observations
  merge_sleep(planned, obs)  → 3계층 우선순위로 최종 수면 타임라인 확정
  infer_sleep_from_steps()   → 수면 로그 없을 때 걸음 수로 대체 추정
  coverage(obs, window)       → 실측 커버리지 비율 (캘리브레이션 UI용)
```

**설계 의도**: `light.py`와 `pressure.py`가 "계획인지 실측인지"를 신경 쓰지 않게 한다. `merge_sleep()`이 이미 결정한 최종 타임라인만 받는다.

### 2-2. 데이터 흐름 변경

```
변경 전
  근무표 ──→ light.plan_sleep() ──→ 계획 수면창 ──┬──→ lux(t) ──→ phase
                                                └──→ pressure

변경 후
  근무표 ──→ light.plan_sleep() ──→ 계획 수면창 ──┐
                                                 ├─→ merge_sleep() ─→ 확정 타임라인 ─┬─→ lux(t) ─→ phase
  헬스데이터 ─→ observations.ingest() ─→ 실측 ────┘                                   └─→ pressure
```

핵심: **분기점이 `merge_sleep()` 하나**다. 여기만 테스트하면 전체 정합성이 보장된다.

## 3. 작업 항목

### P0 — 데모 전 필수

#### P0-1. `merge_sleep()` + lux 보정 연결
- **파일**: `observations.py`(신규), `light.py`
- **작업**: `build_light_schedule()`이 계획 수면창 대신 확정 타임라인을 받도록 시그니처 변경. 실측 수면 구간은 `BEDROOM_LUX`, 실측 각성 구간은 `HOME_AWAKE_LUX` 적용.
- **효과**: 이 한 항목이 실측 정확도 기여분의 대부분.
- **검증**: 동일 근무표 + 실측 취침 3시간 지연 → DLMO 추정치가 지연 방향으로 이동하는지 확인.

#### P0-2. `se_discount()` 실제 연결
- **파일**: `pressure.py`, `pipeline.py`
- **작업**: `ObservedSleep.efficiency`를 `se_discount()`에 실제로 전달. 현재 항상 `None`.
- **주의**: `constants.py`의 `SE_FLOOR`, `SE_REFERENCE`는 `ASSUMPTION` 태그가 붙어 있다. 발표에서 수치 언급 금지, 방향성만 주장.

#### P0-3. API 스키마 확장
- **파일**: `main.py`, `schemas.py`
- **작업**: `POST /plan` 요청에 `observations` 필드 추가 (**optional**). 없으면 기존 동작 그대로.
- **캐시 키**: `pipeline.cache_key`에 실측 해시를 포함시켜야 한다. 안 그러면 실측이 바뀌어도 옛 결과가 나온다. **누락 시 데모 중 "값이 안 변한다" 버그로 직결.**

#### P0-4. `run_in_executor` (기존 미해결 항목)
- **파일**: `main.py`
- 4모델 × ODE = 요청당 수 초. 동기 실행 시 이벤트 루프 차단.
- 실측 통합과 무관하지만 **여전히 미해결**이므로 여기 유지.

### P1 — 있으면 좋음

#### P1-1. 걸음 수 기반 수면 추정
- **파일**: `observations.py`
- 수면 로그 없는 날 `StepCount`의 장시간 0 구간으로 수면창 추정.
- **근거**: Huang 2021 — 교대근무자 표본에서 활동 기반 예측이 광 기반보다 우수.
- 기존 죽은 코드 `scale_steps_to_activity()`를 여기서 살린다.

#### P1-2. 캘리브레이션 커버리지 노출
- **파일**: `pipeline.py`, 응답 스키마
- `coverage()` 결과를 응답에 포함 → 프론트에서 "정확도 62%" 진행도 표시.
- **제품 관점**: 리텐션 장치이자, 추정 불확실성을 정직하게 드러내는 장치.

#### P1-3. 검증 루프 (예측 vs 실제)
- **파일**: `observations.py`
- 모델 DLMO 추정 + 2h ≈ 예상 입면 시각. 실제 입면과의 오차를 누적 기록.
- MVP에서는 **기록만** 하고 모델에 피드백하지 않는다.

### P2 — 로드맵 (해커톤 범위 밖)

- **개인 파라미터 피팅**: 관측 수면/기상 시각을 타깃으로 개인 τ·초기위상 역산. 최소 2~3주 연속 데이터 필요.
- **RHR 기반 위상 검증**: RHR 최저점과 CBT_min 상관. 문헌은 있으나 미확립 (등급 C).
- **CSS 통합**: Song/Hong 계열. 현재 `pressure.py`는 열화 근사임을 명시.

## 4. API 계약

### 요청 (변경분만)

```jsonc
POST /plan
{
  "roster": "DDEENNOO",
  "start_date": "2026-08-17",
  "profile": { "workplace_lighting": "normal", "bedroom_lighting": "curtain" },

  // 신규 — optional. 없으면 기존과 동일 동작
  "observations": {
    "sleep": [
      {
        "start": "2026-08-15T01:30:00+09:00",
        "end":   "2026-08-15T08:10:00+09:00",
        "efficiency": 0.83,        // nullable
        "source": "apple_health"
      }
    ],
    "steps_hourly": [              // optional
      { "hour": "2026-08-15T09:00:00+09:00", "count": 412 }
    ]
  }
}
```

### 응답 (추가분만)

```jsonc
{
  "...": "기존 필드 유지",
  "calibration": {
    "coverage": 0.62,              // 실측이 커버한 시간 비율
    "observed_nights": 9,
    "source_mix": { "measured": 0.62, "declared": 0.31, "default": 0.07 }
  }
}
```

### Flutter 측 계약

- 전송은 **요약본**만. 원시 HealthKit 샘플을 그대로 올리지 않는다.
- 타임존은 반드시 **오프셋 포함 ISO 8601**. 교대근무는 자정 교차가 상시라 naive datetime은 사고 확정.
- 실측 없으면 `observations` 필드를 **생략**한다 (빈 배열 금지 — "측정했는데 없음"과 "측정 안 함"은 다르다).

## 5. 검증 방법

| 항목 | 방법 | 통과 기준 |
|---|---|---|
| lux 보정이 실제로 먹히나 | 동일 근무표, 취침 3h 지연 실측 주입 | DLMO가 지연 방향으로 유의미하게 이동 |
| 부분 데이터 처리 | 16일 중 3일만 실측 | 에러 없이 완주, `coverage` ≈ 0.19 |
| 무데이터 회귀 | `observations` 생략 | 기존 출력과 **바이트 단위 동일** |
| 캐시 정합성 | 실측만 바꿔 재호출 | 캐시 미스 발생 (결과 갱신) |
| 타임존 | KST 자정 교차 수면 구간 | 구간 분할 정상 |

**무데이터 회귀 테스트가 가장 중요합니다.** 이 작업의 실패 모드는 "실측 있는 케이스가 안 되는 것"이 아니라 "실측 없는 기존 케이스가 깨지는 것"입니다.

## 6. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 캐시 키에 실측 미포함 | 데모 중 값이 안 바뀜 | P0-3에서 반드시 처리 |
| 실측 데이터 희소 (개인 export 20개월 중 16박) | 실측 경로가 데모에서 안 보임 | **시드 데모 데이터에 실측을 넣는다** (기존 시드 전략 그대로) |
| `merge_sleep()` 우선순위 로직 복잡화 | 디버깅 지옥 | 슬롯 단위 순수 함수로 작성, 단위 테스트 필수 |
| 실측 반영으로 결과가 "나빠 보임" | 발표 혼선 | 이건 버그가 아니라 기능. "예정과 실제의 괴리를 잡아낸다"가 서사 |
| SE 할인 상수 미검증 | 과장 주장 위험 | 발표에서 수치 언급 금지 |

## 7. 해커톤 범위 결정

**하는 것**: P0 전체 (4개 항목)
**하면 좋은 것**: P1-2 (캘리브레이션 UI) — 시각적 임팩트 대비 구현 비용 낮음
**안 하는 것**: P1-3, P2 전부, 실제 HealthKit 연동

HealthKit 실연동은 물리 기기 + 유료 개발자 계정 + macOS가 필요합니다. **시드 데이터에 실측을 포함시키면 데모에서 이 경로가 전부 살아 있는 것처럼 보이고, 실제로 엔진은 진짜로 그 경로를 탑니다.** 연동 화면 하나만 별도로 보여주면 충분합니다.

## 8. 발표용 서사

> "근무표는 계획이고, 헬스 데이터는 실제입니다.
> 저희 엔진은 근무표만으로 첫날부터 동작하고, 실제 데이터가 쌓이면 계획과 실제의 차이를 잡아냅니다.
> 다만 수면 데이터를 생체시계 모델에 **입력**하지는 않습니다 — 수면은 시계의 결과지 원인이 아니니까요.
> 대신 그 사람이 실제로 언제 불을 끄고 잤는지를 알아내서, **빛 노출 이력을 정확하게 만드는 데** 씁니다."

이 문장이 심사위원에게 "이 팀은 모델을 이해하고 쓰고 있다"를 전달하는 지점입니다.
