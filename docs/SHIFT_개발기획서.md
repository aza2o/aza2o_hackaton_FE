## 0. 문서의 범위

이 문서는 **엔진 완성 이후 앱 구현까지의 계획**을 다룬다. 제품 비전과 사용자 리서치는 별도 PRD에 있으며, 여기서는 그것을 전제로 아키텍처 결정 · 기능 명세 · 구현 범위 · 리스크를 확정한다.

이미 확정된 것과 아직 열려 있는 것을 명시적으로 구분한다. 열려 있는 항목은 §10에 모아두었다.

## 1. 문제 정의

3교대 간호사(Day/Evening/Night/Off)는 근무표에 따라 광 노출과 수면 시각이 주 단위로 뒤바뀐다. 이때 발생하는 문제는 "잠을 적게 잔다"가 아니라 **"몸의 시계와 근무 시각이 어긋난다"**는 것이다.

기존 수면 앱들이 이 집단에 실패하는 이유는 세 가지다.

| 한계 | 내용 |
|---|---|
| 사후적 | 어제 잘 잤는지 보여줄 뿐, 내일 언제 자야 하는지 말하지 못한다 |
| 규칙적 수면 전제 | 매일 같은 시각에 자는 사용자를 가정한 모델 |
| 광 노출 측정 실패 | 손목 센서는 실내 근무 중 광량을 사실상 0으로 반환한다 |

### 핵심 착안

간호사는 **다음 달 근무표를 이미 알고 있다.** 이것이 이 도메인의 결정적 비대칭이다. 확정된 미래 로스터를 모델 입력으로 쓰면 위상을 사전에 예측할 수 있고, 개입 시점을 **미리** 제안할 수 있다. 사후 리포트가 아니라 사전 처방이 된다.

### 경쟁 지형

- **Timeshifter Shift Work** — 가장 가까운 글로벌 유사 제품. 한국 시장 존재감 없음.
- **KAIST 김재경 연구실 / 갤럭시워치 연동(2025)** — 선행 연구이자 정당성 근거. 다만 로스터 사전 입력 개념은 없다.

로스터 사전 입력을 모델 입력으로 삼는 접근은 선행 문헌에 전례가 없다. **차별점인 동시에 리스크**로 기록한다(§9).

## 2. 대상 사용자

**MVP 대상**: D/E/N/O 순환 3교대 간호사

**MVP 제외**:

- **야간전담(나이트킵)** — 순환하지 않으므로 위상 동역학이 근본적으로 다르다. 별도 세그먼트로 분리하며, 설문 데이터도 분리 분석한다.
- 2교대 · 12시간 교대 — 온보딩에서 사용자 정의 시각 입력으로 부분 수용하되 검증 대상 아님

> 온보딩은 근무 시각을 **하드코딩하지 않는다.** 병원마다 D/E/N 시각이 다르므로 사용자 정의를 기본으로 한다.

## 3. 핵심 아키텍처 결정

이 네 가지는 확정 사항이며, 뒤집으려면 문서를 개정해야 한다.

### 3-1. 로스터가 곧 광 스케줄이다

lux(t)를 센서로 측정하지 않고 **생성**한다.

```
lux(t) = f(로스터, 온보딩 조명 상수, NOAA 일출·일몰 근사)
```

실내 근무자에게는 이쪽이 손목 센서보다 정확하고, 무엇보다 **미래에 대해 계산 가능**하다. 센서는 과거만 알지만 로스터는 미래를 안다.

### 3-2. 웨어러블은 검증 신호다

`TimeInDaylight`, HRV, 안정시 심박, 수면 단계는 **모델 입력이 아니라 예측 검증용**이다. 이 구분이 무너지면 센서 결측이 곧 모델 실패가 된다.

부수 효과로, 웨어러블이 없는 사용자도 코어 기능을 온전히 쓸 수 있다.

### 3-3. 계산은 서버에서 한다

Arcascope `circadian`(MIT, v1.0.3)이 Python이므로 Dart 포팅은 재현성을 해친다. Walch/Hannay 저자 계보를 통한 검증 가능성을 유지하기 위해 서버 계산을 유지한다.

넛지는 하루 1회 계산이면 충분하므로 지연은 문제가 되지 않는다.

### 3-4. 넛지는 반증적 시뮬레이션으로 만든다

PRC(위상반응곡선)가 아니라 **counterfactual simulation**이다. "이 사람이 이 날 20시에 밝은 빛을 쬐면 DLMO가 얼마나 이동하는가"를 개인별·일자별로 계산한다.

x축이 시계 시각이므로 그대로 알림 시각이 된다. PRC는 x축이 일주기 위상이라 사용자에게 직접 제시할 수 없다.

## 4. 시스템 구성

```
┌─────────────────────────────────────────┐
│  Flutter 앱                              │
│  ├ 로스터 입력/확인                        │
│  ├ 액토그램 (CustomPainter)               │
│  ├ 넛지 카드                              │
│  ├ 로컬 알림 예약 (flutter_local_notif.)   │
│  └ [Swift 채널] HealthKit TimeInDaylight  │
└──────────────┬──────────────────────────┘
               │ 하루 1회 동기화
┌──────────────▼──────────────────────────┐
│  FastAPI (Railway / Fly.io)              │
│  ├ lux(t) 생성                            │
│  ├ 4개 모델 병렬 실행                       │
│  │   Hannay19(주) / Hannay19TP /          │
│  │   Forger99 / Jewett99                  │
│  ├ Process S (Two-Process 근사)           │
│  └ 반증 시뮬레이션 → 넛지 스케줄            │
└──────────────┬──────────────────────────┘
               │
┌──────────────▼──────────────────────────┐
│  Supabase (Auth / Postgres)              │
└─────────────────────────────────────────┘
```

### 동기화 전략

**하루치 넛지 스케줄을 통째로 받아 로컬에 캐시한 뒤, 로컬 알림으로 예약한다.**

iOS는 백그라운드 실행 시점을 보장하지 않으므로 "최신 센서 데이터로 실시간 재계산" 설계는 성립하지 않는다. 서버가 미리 계산하고 클라이언트는 예약만 담당한다. 이 구조 덕분에 오프라인에서도 넛지가 정상 발화한다.

## 5. 기능 명세

근거 등급: **A** = 임상 가이드라인/RCT 근거 · **B** = 관찰연구/기전 근거 · **C** = 근거 부족, 제품 판단

### 5-1. 온보딩 · 근거 A/C

| 항목 | 수집 내용 |
|---|---|
| 근무 시각 정의 | D/E/N 각각의 시작·종료 (사용자 정의) |
| 조명 환경 | 근무지 조도, 출퇴근 광 노출, 침실 암막 여부 |
| 크로노타입 | 축약형 설문 |
| 카페인 습관 | 섭취 시각 패턴 |

**콜드스타트 처리**: 온보딩 선언값 위에 실시간 캘리브레이션을 덧씌운다. 첫 주 추천은 문헌 상수 기반 개입으로만 제한하고, **캘리브레이션 진행도를 화면에 노출해 리텐션 장치로 쓴다.**

### 5-2. 로스터 입력 · 근거 A

입력 경로와 무관하게 **반드시 사용자 확인·수정 화면을 거친다.** 로스터가 틀리면 모든 예측이 틀리기 때문에, 여기서만큼은 자동화보다 정확성이 우선이다.

| 우선순위 | 경로 | 비고 |
|---|---|---|
| 1차 | **엑셀 파일 업로드** | 실제 병동 근무표가 배포되는 주 형식 |
| 2차 | 패턴 선택 + 캘린더 직접 편집 | 항상 사용 가능한 폴백 |
| 3차 | 근무표 이미지 OCR | `google_mlkit_text_recognition`, 한국어 모델 번들 필요 |

엑셀을 1차로 올리는 이유는, 국내 병동 근무표가 대개 수간호사가 작성한 `.xlsx`/`.xls` 파일로 배포되고 **간호사들이 이미 그 파일을 카카오톡으로 받아 보관하고 있기** 때문이다. 사용자가 이미 가진 것을 그대로 받는 것이 가장 마찰이 적다.

#### 5-2-1. 파일 수신 경로

카카오톡에서 받은 파일을 앱으로 넘기는 경로가 핵심이다.

- **앱 내 파일 선택** — `file_picker`. 구현 간단, 사용자 단계 많음
- **공유 시트 진입** — 카카오톡에서 파일 길게 눌러 "SHIFT로 열기". **iOS Share Extension + Android `intent-filter` 필요 (네이티브 작업, §7-3)**

공유 시트 경로가 압도적으로 편하지만 네이티브 작업이 추가된다. **MVP는 파일 선택만 구현하고 공유 시트는 후순위로 둔다.**

#### 5-2-2. 파싱 위치 — 서버

클라이언트가 아니라 **FastAPI에서 파싱한다.** 근거는 두 가지다.

- 병원마다 양식이 제각각이라 파싱 규칙을 자주 고쳐야 하는데, 서버면 앱 배포 없이 즉시 반영된다
- Dart `excel` 패키지는 구형 `.xls`(BIFF)를 읽지 못한다. 국내 병원에 `.xls`가 아직 많아 **클라이언트 파싱은 시작부터 상당수를 놓친다.** Python은 `openpyxl`(.xlsx) + `xlrd`(.xls)로 양쪽을 덮는다

#### 5-2-3. 양식 문제

병동 근무표는 사람이 보라고 만든 파일이라 기계에 적대적이다. 파서가 반드시 처리해야 하는 것들:

| 문제 | 대응 |
|---|---|
| 피벗 구조 (행=간호사, 열=1~31일) | 헤더 행 자동 탐지 후 전치 |
| 병합 셀, 다중 헤더, 상단 병동명 | 날짜 행을 앵커로 삼아 오프셋 계산 |
| 우측 합계 열 (D수/N수/OFF수) | 날짜 범위 밖 열은 폐기 |
| 연도 누락 (1~31만 존재) | **사용자에게 연·월 확인 요구** |
| 본인 행 식별 | 이름 매칭 실패 시 행 선택 UI 제시 |

**근무 코드 매핑 테이블**이 별도로 필요하다. `D/E/N/O` 외에 `데이/이브/나이트/오프`, `주/저/야/휴`, 연차·교육·병가 표기가 병원마다 다르다. **미등록 코드는 임의 추측하지 않고 사용자에게 물어 매핑을 학습**시킨다. 이 매핑은 사용자 단위로 저장해 다음 달부터 재사용한다.

#### 5-2-4. 개인정보 — 설계 제약

> **근무표 파일에는 같은 병동 동료 전원의 근무 일정이 들어 있다.** 즉 제3자의 개인정보를 업로드받는 구조다.

다음을 강제한다.

- 서버는 **본인 행만 추출한 뒤 원본 파일을 즉시 폐기**한다. 저장하지 않는다
- 타인 행은 어떤 형태로도 DB에 남기지 않는다
- 업로드 화면에 이 처리 방식을 명시하고 동의를 받는다
- 로그에 파일 내용을 남기지 않는다

이 제약은 성능이나 편의와 교환하지 않는다.

### 5-3. 액토그램 · 근거 B

이중 플롯 액토그램. 수면 구간, 근무 구간, 예측 DLMO를 한 화면에 겹쳐 보여준다. **제품의 시그니처 비주얼이자 데모의 핵심.**

`fl_chart`로는 구현 불가. `CustomPainter` 직접 구현.

### 5-4. 넛지 · 근거 A/B

하루 2~3개. 각 넛지는 다음을 포함한다.

- 행동 (밝은 빛 / 암막 / 블루라이트 차단 / 카페인 컷오프 / 수면 시각)
- 실행 시각 창
- **예상 효과** ("DLMO 약 40분 지연")

#### 검증된 효과 크기

| 근무 유형 | 개입 효과 |
|---|---|
| Day | ≤12분 — 거의 무의미. **넛지를 남발하지 않는다.** |
| Night | 근무 전 저녁 창에서 유의미. 20시 밝은 빛 시 최대 약 42분 지연 |

효과가 없는 날에 알림을 보내지 않는 것이 알림 피로를 막는 유일한 방법이다.

#### 수면 추천 프레이밍

**"얼마나"가 아니라 "언제"**로 통일한다 (Hong 2021 CSS, Song 2025 SleepWake). DLMO 추정치를 권장 취침 앵커로 사용한다.

### 5-5. 피부 · AAC 트랙 · 근거 C

수면 데이터와 스킨케어 루틴을 연결하고 제품을 추천한다. 브랜드 트랙의 주 차별화 요소.

> **정직한 기술**: 교대 유형별로 스킨케어를 차등화할 동료심사 근거는 현재 없다. Oyetakin-White 2015(수면-피부 장벽)까지가 근거의 한계이며, 그 이상은 제품 판단이다. 발표 시 이 등급을 숨기지 않는다.

### 5-6. 명시적 제외

- 심수면/REM 단계 화면 — 웨어러블 측정 신뢰도 부족
- 절대 조도 비교 — 기기 간 비교 불가
- 야간전담 세그먼트 — §2

## 6. 플랫폼 전략

### 6-1. Flutter 확정

UI 렌더링 일관성, 핫 리로드, `CustomPainter` 기반 액토그램 구현 이점. 남는 네이티브 작업은 Swift 채널 1개 수준으로, 프레임워크 전환 비용이 절감 효과를 상회한다.

### 6-2. 공유 범위 — 단일 코드베이스

**앱을 두 개 만드는 것이 아니다.** 온보딩, 로스터, 엑셀 업로드, 액토그램, 넛지 카드, 상태관리, 서버 계산은 100% 공유된다.

특히 §3-1의 결정(로스터가 곧 광 스케줄) 덕분에 **위상 예측·DLMO·넛지 스케줄은 기기와 무관하게 동일하다.** 비대칭은 §3-2의 검증 레이어에만 닿는다.

| 영역 | 분기 |
|---|---|
| UI · 로스터 · 액토그램 · 넛지 · 서버 계산 | ❌ 공유 |
| 헬스 데이터 어댑터 | ✅ 분기 |
| 권한 플로우 | ✅ 분기 |
| 알림 권한 (정확알람 · 절전 예외) | ✅ 안드로이드만 |

추가 공수는 헬스·알림 레이어에서 20~30%, 전체로는 한 자릿수 후반 %다. **다만 테스트 공수는 두 배**이며, 안드로이드는 제조사별 편차까지 확인해야 한다.

### 6-3. 플랫폼별 헬스 데이터 차이

| 신호 | iOS (HealthKit) | Android (Health Connect) |
|---|---|---|
| 일광 노출 | `timeInDaylight` (Swift 채널, §7-1) | **타입 자체가 없음** |
| 수면 단계 | 심수면 / `asleepCore` / REM / 각성 | 심수면 / 얕은잠 / REM / 각성 |
| 수면 세션 | **없음 — 구간을 직접 이어야 함** | `SleepSessionRecord` (세션이 중심 레코드) |
| 침대 안/밖 | `SLEEP_IN_BED` | `AWAKE_IN_BED`, `OUT_OF_BED` |
| HRV | SDNN (애플워치 필요) | RMSSD |
| 안정시 심박 | 지원 | 지원 |
| 수면 중 체온 | 손목 온도 (읽기 전용) | 피부 온도 (기기 의존) |

#### 타입 목록보다 중요한 구조적 차이

**(a) 수면 데이터 모델이 반대다.** Health Connect는 `SleepSessionRecord`가 시작·종료 시각과 단계를 담는 중심 레코드다. HealthKit은 카테고리 샘플이 흩어져 있어 **"이것이 한 번의 수면인가"를 앱이 직접 판정해야 한다.** 교대근무자는 낮잠·분할수면이 잦아 이 판정이 특히 어렵다. SHIFT는 수면 시각을 앵커로 쓰므로 iOS 어댑터에 **세션 스티칭 로직**이 별도로 필요하다.

**(b) 출처 다양성.** iOS는 사실상 애플워치 단일 공급원이라 알고리즘이 일관된다. Android는 삼성헬스·핏빗·가민·구글핏이 같은 저장소에 쓴다. 결과적으로 사용자마다 다른 알고리즘의 수면 단계가 들어오고, 같은 밤이 두 앱에서 중복 기록될 수 있다. **개인 내 상대 비교 원칙이 안드로이드에서는 선택이 아니라 필수다.** 어댑터에 dedup + 출처 필터를 넣는다.

**(c) 권한 확인 불가 — iOS.** HealthKit은 프라이버시 보호를 위해 읽기 권한 거부 여부를 앱에 알리지 않고 빈 결과를 반환한다. 즉 **iOS에서는 "권한 미부여"와 "시계를 안 참"을 구분할 수 없다.** Health Connect는 부여된 권한 조회가 가능하다.

> 캘리브레이션 진행도를 리텐션 장치로 쓰기로 했으므로(§5-1), iOS에서는 "데이터 없음"의 원인을 특정할 수 없다. **안내 문구는 두 원인을 모두 커버하도록 작성한다.**

**(d) 이력 범위.** iOS는 권한만 있으면 과거 전체를 읽는다. Health Connect는 기본 30일이며 그 이상은 `READ_HEALTH_DATA_HISTORY` + `requestHealthDataHistoryAuthorization()`이 필요하다.

**(e) 동기화 지연.** 갤럭시워치 수면 데이터는 기상 시 워치에서 생성된 뒤 페어링된 폰으로 전송되어야 처리된다. **아침에 앱을 열자마자 어젯밤 데이터가 있다고 가정하지 않는다.**

**(f) HRV는 이름만 다른 것이 아니다.** SDNN은 전체 변동성, RMSSD는 부교감 활성에 더 직접 반응하며 **상호 변환 공식이 없다.** 애플은 SDNN을 산발적으로만 기록한다. 두 값에 공통 임계값을 쓰면 조용히 틀린다. **플랫폼별 정규화 후 개인 내 z-score로만 취급한다.**

### 6-4. 어댑터 계약

분기는 인터페이스 뒤로 숨긴다. UI는 `capabilities`만 보고 검증 카드 노출 여부를 결정한다.

```dart
abstract class HealthSignalSource {
  HealthCapabilities get capabilities;

  /// iOS: 세션 스티칭 후 반환 / Android: SleepSessionRecord 정규화 + dedup
  Future<List<SleepSession>> sleepSessions(DateRange range);

  /// null = 이 기기가 제공하지 않음 (Android는 항상 null)
  Future<DaylightSeries?> daylight(DateRange range);

  /// 원시값이 아닌 개인 내 z-score. 플랫폼별 정규화는 구현체 책임
  Future<HrvSeries?> hrvNormalized(DateRange range);

  Future<HeartRateSeries?> restingHeartRate(DateRange range);
}

class HealthCapabilities {
  final bool hasDaylight;
  final bool canVerifyPermission;   // iOS = false
  final Duration maxHistory;         // Android 기본 30일
  final HrvMetric hrvMetric;         // sdnn | rmssd | none
}
```

구현체는 `IosHealthSource` / `AndroidHealthSource` 두 개. **원시값은 인터페이스 밖으로 내보내지 않는다** — SDNN과 RMSSD가 같은 필드로 새어나가는 순간 상위 로직이 오염된다.

### 6-5. 사용자 대면 프레이밍

문서상으로는 "안드로이드 축소 모델"이지만, **제품에서 그렇게 보여서는 안 된다.**

검증 레이어를 "iOS 전용 기능"이 아니라 **"광 노출 검증 — 지원 기기에서 사용 가능"**이라는 선택적 애드온으로 노출한다. 애플워치 없는 아이폰 사용자도 동일한 상태이므로, **플랫폼이 아니라 기기 보유 여부로 가르는 것이 실제로 더 정확하다.**

이 비대칭을 문서에 명시하는 이유는, "왜 안드로이드는 정확도가 다른가"라는 질문에 방어하기 위해서다.

## 7. 네이티브 작업 범위

### 7-1. Swift MethodChannel (필수 · 1~2일)

`HKQuantityTypeIdentifierTimeInDaylight`를 `HKStatisticsCollectionQuery`로 조회. Flutter `health` 패키지(v13.3.2)에 해당 타입이 없어 직접 구현한다.

**즉시 스파이크로 검증할 것.** 이게 막히면 광 신호 검증 스토리가 통째로 빠진다.

### 7-2. 알림 스케줄링 (필수 · 제품의 심장)

| 항목 | 대응 |
|---|---|
| iOS pending 64개 제한 | 하루 3개 = 약 3주치. 앱 실행 시 재예약 로직 필수 |
| Android 12+ 정확 알람 | `USE_EXACT_ALARM`은 알람/시계 앱 전용 정책. `SCHEDULE_EXACT_ALARM` + 사용자 수동 허용 UI 필요 |
| 삼성 절전 정책 | 갤럭시 비중이 절대적인 타깃. **온보딩에 배터리 최적화 예외 요청 화면 포함** |
| 타임존 | `timezone` 패키지 초기화. 자정을 넘는 야간 근무 처리 검증 |

### 7-3. 공유 시트 진입 (후순위)

카카오톡에서 받은 근무표 파일을 "SHIFT로 열기"로 넘기는 경로. iOS는 Share Extension 타깃 추가, Android는 `intent-filter` + `receive_sharing_intent` 계열 플러그인이 필요하다.

**MVP 범위 밖.** 다만 실사용 마찰을 가장 크게 줄이는 항목이므로, 시연에서 "다음 단계"로 언급할 가치가 있다.

### 7-4. 데모 모드 (권장)

시드 데이터로 전 기능이 도는 모드를 앱 내에 내장한다. 해커톤 시연은 HealthKit 권한이나 실기기 문제로 죽는 경우가 많다. 웹 백업을 따로 만드는 것보다 훨씬 싸게 같은 리스크를 막는다.
